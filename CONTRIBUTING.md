# Contributing

## Setup

Requires Node `>=18` (repo is pinned to `24.11.0` via `.nvmrc` and CI runs on
Node 24). This project uses `yarn` in CI/Docker but `npm` scripts locally both work
against the same `package.json`; pick one and don't mix lockfiles.

```bash
nvm use
npm install   # or: yarn install
```

Ignore `Dockerfile` / `docker-compose.yml` / the `up`/`down` Makefile targets — they're
leftover boilerplate from the npm-package template this repo was bootstrapped from
and describe an unrelated React app. See
[docs/ARCHITECTURE.md](./docs/ARCHITECTURE.md#things-that-look-load-bearing-but-arent).

## Everyday commands

| Command | What it does |
|---|---|
| `npm run build` | Builds `dist/` (cjs + esm + `.d.ts`) via `tsup`, then verifies the output is importable from CJS, ESM, and TS consumers |
| `npm test` | Runs the unit suite (`tests/`) with coverage, excluding `tests_integration/` |
| `npm run test:integration` | Runs `tests_integration/` (hits real fixture data pulled from a production-shaped record — see `tests_integration/production_record/readme.md`) |
| `npm run test:watch` | Jest in watch mode |
| `npm run lint` | ESLint over `src/` and `tests/`, auto-fixing |
| `npm run typecheck` | `tsc --noEmit` |
| `make lint` | Runs `npm run lint` + `npm run typecheck` under the pinned Node version |

Run `npm run lint && npm run typecheck && npm test` before opening a PR — this is
exactly what `node-ci.yml` runs on every push/PR to `main`.

## Git hooks

Husky + `lint-staged` are wired up via `npm run prepare` (runs automatically on
`npm install`). On every commit, staged `.ts`/`.js` files under `src/**` and
`test/**` are auto-fixed with ESLint (`.husky/pre-commit` → `npx lint-staged`,
config in `package.json`'s `lint-staged` key). If a commit is rejected, it's
because lint-staged found something it couldn't auto-fix — read the ESLint output.

## Commit messages

This repo follows [Conventional Commits](https://www.conventionalcommits.org/)
(`feat:`, `fix:`, `build:`, etc.) — see the `release.plugins` config in
`package.json` for how commit types map to changelog sections. Run `npm run cm`
(commitizen) if you want an interactive prompt instead of writing the message
by hand.

## Adding or modifying an IPS section

See [docs/adding-a-new-ips-section.md](./docs/adding-a-new-ips-section.md) — there
are several places a new section must be registered, and missing one fails
silently or throws only at runtime.

## FHIR types

`src/types/` is a large tree of hand-maintained TypeScript types mirroring FHIR R4
resources/partials (each file is marked
`// This file is auto-generated by generate_types so do not edit manually`, but the
generator script referenced by `make generate_types`
(`src/generator/generate_types.py`) doesn't currently exist in this repo — don't
rely on it). If a resource is missing a field you need, edit the corresponding file
under `src/types/resources/` or `src/types/partials/` directly.

## CI / release

- `node-ci.yml` — lint + typecheck + test, on every push/PR to `main`.
- `codeql-analysis.yml` — scheduled + on-push security scanning.
- `npm-publish.yml` — builds and publishes to npm **only when a GitHub Release is
  manually published**. The `semantic-release` config in `package.json` is not
  currently invoked by any workflow in this repo — don't assume merging to `main`
  publishes a new version automatically.
